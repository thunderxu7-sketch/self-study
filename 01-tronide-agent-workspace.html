Interview detail 01 · Agent 产品设计与系统架构

TronIDE Agent Workspace

面试不要把它讲成“给 IDE 加一个聊天框”。更准确的定位是：以 session 为边界、以 task 为执行单元、以 artifact 为证据载体，并把钱包、文件和主网写操作关进策略与人工确认里的 Agent 工作区。

01
Data model

session、artifact、task 如何建模？

Session 是连续工作上下文，Task 是可执行的意图，Artifact 是可审查、可复用的结果。 三者不能都做成一条聊天消息：聊天是交互层，模型调用是执行层，artifact 才是交付和审计层。

  • Session：绑定用户、workspace、目标网络、权限策略快照、事件流和生命周期；一次 session 可以继续多个 task。
  • Task：包含用户意图、结构化计划、当前步骤、tool calls、审批状态、预算/超时和最终 outcome；失败后只允许从明确 checkpoint 恢复。
  • Artifact：文件 diff、编译 ABI/bytecode、测试报告、部署候选、交易预览或链上交易结果；每个 artifact 带版本、内容 hash、来源和状态。
  • 关键关系：审批绑定的是“不可变的 action/artifact digest”，不是模糊的自然语言；宣称“已上链”必须有 txid 和网络信息。
Sessionidentity · workspace · network · policy snapshot · event stream
→
Taskintent · plan · step · tool calls · approval · outcome
→
Artifactdiff · build · test · tx preview/result · hash · provenance

02
Runtime architecture

Tool、Skill、Orchestrator 如何划分？

Tool：窄而确定的能力

例如读取文件、编译、读取诊断、调用 view、构建交易、请求钱包签名。Tool 只做一件事，声明输入 schema、权限、side effect、超时和输出。

Skill：可复用的业务打法

例如“部署前检查”或“合约测试闭环”。Skill 描述什么时候调用哪些 Tool、顺序、前置条件、停止条件、错误恢复和成功证据；它要版本化。

Orchestrator：运行时状态机

负责选下一步、执行 tool、持久化事件、应用 policy、控制预算和超时、进入 approval gate，以及在安全 checkpoint 处恢复。

边界原则

模型可以提出下一步，但不能绕过 Orchestrator 直接 shell、直接拿私钥或直接修改审计记录。所有副作用都必须从 Tool 的声明进入。

→
Orchestratorpolicy · state · budget · approvals · events
→

03
Irreversible side effects

为什么主网写操作不能自动重试？

因为“请求超时”不等于“链上没有发生”。签名之后、广播之后，客户端可能丢失响应，但节点或钱包已经接受交易；此时重新构造并签名一笔新交易，可能造成重复转账、重复授权或重复业务动作。

阶段可以做什么处理原则
读 / 模拟 / 编译有限重试只有确定无副作用，且错误属于 transient/rate limit 时才指数退避。
签名前重新构建可刷新余额、费用、nonce，但仍要重新展示预览并获得确认。
签名后或广播超时禁止自动重试先按 txid、raw tx、nonce 和交易指纹对账；状态未知时交给人工或显式恢复命令。
已确认失败不复制动作把链上 revert 当业务结果，修正参数后由用户发起新意图。

// 伪代码：只在确认“无副作用”时允许重试
const attempts = requestContext.idempotent ? 2 : 1;
for (let i = 0; i < attempts; i += 1) {
  try {
    return await httpCall();
  } catch (err) {
    if (i + 1 === attempts || !isRetriableReadError(err)) throw err;
    await backoffWithJitter(i);
  }
}

// broadcast timeout: query existing state; do not construct a new write.
return { status: "unknown", nextAction: "manual-reconcile" };
面试关键词：unknown outcome、transaction reconciliation、exactly-once illusion、不可逆副作用。不要承诺“至少一次重试”，要承诺“未知状态先对账”。
04
Governance & human control

权限、文件边界和人工确认如何落地？

  1. 权限：把 actor、workspace、network、tool、最大费用、风险等级和审批状态放进可执行的 PolicyDecision；默认最小权限，主网写默认 deny。
  2. 文件边界：所有路径先 canonicalize，再检查 workspace root；拒绝 ..、越界 symlink、密钥文件和 .env。写文件先生成 diff，不能让模型直接覆盖原文件。
  3. 人工确认：低风险读取自动执行；本地修改展示 diff；测试网部署显示网络和交易预览；主网写入必须展示 selector、参数、费用、资产影响、artifact hash，并由用户在钱包/Review mode 确认。
  4. 审计：记录 requestId、session/task、policy version、tool/schema version、输入摘要、输出、用户决定、txid 和时间；敏感值只存 hash/脱敏摘要。

低风险自动化

读源码、编译、静态检查、本地测试、Nile view 调用。失败可保留诊断并继续修复，但必须受 timeout、预算和文件 root 约束。

高风险人工闸门

导出签名交易、部署、转账、授权、升级合约和主网写入。用户拒绝后任务进入 stopped/rejected，不能由模型换一个参数悄悄重来。

最终边界：Agent 可以生成代码、计划和交易候选；用户/钱包才拥有签名权，Orchestrator 才拥有执行编排权，审计系统拥有不可变的事实记录。
