01
Side-effect separation

read、simulate、write 为什么必须分离？

三者都可能长得像“调用合约”，但风险和恢复方法完全不同。把它们塞进一个万能 call，模型就无法知道什么时候可以重试、什么时候必须停下来让人签名。

通道含义默认权限与恢复
read链上 view、余额、市场和账户信息；不签名、不广播。可缓存、可在 transient/rate limit 时有限重试。
simulate构建 calldata 并做 constant/preflight；可以得到 revert、selector、energy/fee 预估。不移动价值、不持有 signer；失败通常是参数或业务条件问题。
write构建交易、请求签名、广播并跟踪确认。必须显式确认；签名/广播后的未知状态禁止自动生成第二笔交易。

→

→
WRITEpreview → approval → sign → broadcast
no automatic retry

关键代码：先返回 dry-run，再进入 signer 和 broadcast（精简自实际实现）

async function sendContractTx(params, opts) {
  if (opts.dryRun) {
    return dryRunContractTx(params, owner); // no signer / no broadcast
  }

  const built = await buildTx(params);
  await runPrecheck(built);                 // balance, fee, revert
  await confirmProceed(preview(built), opts.yes);

  const signed = await signer.signTransaction(built);
  if (!opts.broadcast) {
    return { status: "signed", signedTx: redact(signed) };
  }
  return await broadcastTx(signed);
}
我会在 Tool schema 里显式写 sideEffect: read | simulate | write，而不是靠工具名猜。Agent 可以自动编排 read/simulate，但 write 必须走单独的 approval policy。

02
Transaction state & recovery

交易失败、超时、重复广播如何处理？

先分类，再动作。 “失败”至少要区分输入错误、模拟 revert、签名被拒、广播明确失败、广播结果未知、链上确认失败。只有前两类可以直接修参数；广播未知时，第一动作永远是对账，不是重签。

事件分类策略
schema/参数错误、权限失效确定性失败不重试，返回字段级 hint，让上层修正。
read RPC 5xx、rate limit、瞬时网络异常可重试指数退避 + jitter，次数和总预算有上限。
simulate revert业务/参数失败记录 revert reason，回到预览或人工确认，不盲目重放。
钱包拒签/断开用户/依赖失败停止当前 task；用户重新发起时重新展示预览。
广播超时、客户端断线未知状态按 txid/raw tx/nonce/指纹查询；在结论前禁止生成新 write。
链上 confirmed revert已发生的失败当成业务结果入账，不复制动作；修参数后创建新意图。

防重复广播

给每次用户意图生成持久化 intent key；记录 owner、network、method、参数摘要、fee、nonce 和 signed tx fingerprint。对账完成前，对同一 intent 加锁。

不要伪造 exactly-once

客户端最多做到“同一意图不静默创建第二笔”；最终是否上链要以节点确认和链上状态为准，而不是以本地 HTTP 返回为准。

最容易被追问的边界：签名前失败可以重建；签名后失败只能查询和对账。 如果用户明确要求重发，也应先显示“可能已经成功”的风险。

03
Contract, idempotency & audit

如何做 schema、幂等、审计和错误恢复？

  1. Schema：每个 Tool 有严格的 input schema；输出统一携带 schemaVersion、tool，成功走 result，失败走 error/errorCode/retryable/hint。输入未知字段默认拒绝，避免模型“猜参数”。
  2. 幂等：只给无副作用 HTTP 请求加 idempotent=true；签名和广播永远不标记为幂等。写操作记录 intent/action digest 和 signed tx fingerprint，状态未知时只做 reconciliation。
  3. 审计：requestId、session/task、actor、network、tool/schema version、脱敏输入摘要、输出、policy decision、approval、txid、block 和时间组成一条 append-only evidence。
  4. 错误恢复：把“可重试”和“需要人工处理”分开；读任务可以从 checkpoint 继续，写任务从 unknown 状态进入对账，而不是从头运行。

Skills 层的价值

把“先查账户 summary，再解释 shortfall”这样的业务规则写进版本化 Skill；MCP server 只保证工具契约，Skill 决定业务顺序和停止条件。

安全输出

CLI JSON/quiet 模式拒绝没有显式 consent 的 value-moving write；签名交易默认脱敏，并提示任何拿到 raw signed tx 的人都可能在过期前广播。

可复述的工程判断：schema 约束“能不能调用”，policy 约束“该不该调用”，state machine 约束“调用后怎么办”，audit 约束“事后能不能证明”。
